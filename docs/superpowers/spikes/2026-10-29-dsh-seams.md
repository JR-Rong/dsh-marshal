## 接缝 1：`ws` 能否直接消费 `registerUpgrade` 的 `Duplex`

### 结论：OK

### 证据

1. **DSH 交出来的是什么。** `WebUpgradeRoute.handler` 的类型是 `(req, socket: Duplex, head: Buffer)`（`<dsh-checkout>/packages/host/webserver/src/index.ts:77-83`）。分派处直接把 `node:http` 的 `'upgrade'` 事件参数透传，没有包装：

   ```ts
   this.server.on('upgrade', (req, socket, head) => {      // :584
     …
     Promise.resolve(route.handler(req, socket, head))     // :609
   ```

   所以运行时 `socket` 是真实的 `net.Socket`（TLS 时是 `TLSSocket`），类型上被收窄成 `Duplex`。

2. **DSH 自己就在做同一件事。** gateway 注册 `/api/remote.mux` 升级路由（`<dsh-checkout>/packages/api/gateway/src/index.ts:273-309`），把该 `Duplex` 直接交给 `ws`：

   ```ts
   // <dsh-checkout>/packages/api/gateway/src/stream-server.ts
   this.server = new WebSocketServer({ noServer: true, … })                       // :77-82
   handleUpgrade(req: IncomingMessage, socket: Duplex, head: Buffer, peer) {      // :94
     this.server.handleUpgrade(req, socket, head, (websocket) => { … })           // :95
   ```

   即"`webServer.registerUpgrade` → `new WebSocketServer({noServer:true}).handleUpgrade`"在 DSH 中是既有生产路径，不是我们的新发明。

3. **`ws` 不硬依赖 `net.Socket` 专有成员。** `ws` 8.21.3 的 `setSocket` 明确写了"这些方法在 socket 只是 `Duplex` 时可能不存在"，并逐一 `if` 保护（`<dsh-checkout>/node_modules/.pnpm/ws@8.21.3/node_modules/ws/lib/websocket.js:244-248`）：

   ```js
   // These methods may not be available if `socket` is just a `Duplex`.
   if (socket.setTimeout) socket.setTimeout(0);
   if (socket.setNoDelay) socket.setNoDelay();
   ```

   `grep -rn "setNoDelay\|_handle" ws/lib/*.js` 只命中 `websocket.js:247-248` 这两行；`_handle` 零命中。

4. **最小脚本验证（脚本在 `/tmp`，未提交）。** `http.createServer` + `server.on('upgrade')`，同一份代码跑两种 socket：

   ```js
   import http from 'node:http'
   import { Duplex, PassThrough } from 'node:stream'
   import { WebSocketServer } from 'ws'

   const wss = new WebSocketServer({ noServer: true })
   http.createServer().on('upgrade', (req, socket, head) => {
     // 把真实 socket 藏到一个普通 Duplex 后面：它没有 setTimeout / setNoDelay
     const toWs = new PassThrough(), fromWs = new PassThrough()
     socket.on('data', (c) => toWs.write(c))
     socket.on('end', () => toWs.end())
     socket.on('close', () => { toWs.destroy(); fromWs.destroy() })
     fromWs.on('data', (c) => socket.write(c))
     const target = Duplex.from({ readable: toWs, writable: fromWs })
     wss.handleUpgrade(req, target, head, (ws) => {
       ws.on('message', (m) => ws.send(`echo:${m}`))
       ws.send('hello')
     })
   })
   ```

   输出（真 `ws` 客户端收发）：

   ```
   {"socket":"net.Socket","upgraded":true,"hello":true,"echo":true,"error":null}
   {"socket":"Duplex","upgraded":true,"hello":true,"echo":true,"error":null,
    "target":{"isNetSocket":false,"setTimeout":"undefined","setNoDelay":"undefined","write":"function"}}
   ```

   两种模式下：`handleUpgrade` 回调触发、状态 OPEN、服务端 `hello` 到达客户端、客户端 `ping` 被服务端解析并回 `echo:ping`。即 `ws` 只要求可读可写的 `Duplex`。

### 一个坑（会影响测试替身）

首次按计划字面做法——把**同一个** `PassThrough` 既当读端又当写端传给 `handleUpgrade`——会失败：`PassThrough` 是回环，`ws` 写出的 101 响应又被自己的 receiver 读回去当客户端帧，报 `WS_ERR_EXPECTED_MASK`。这是测试装置的方向混叠，不是 `ws` 的限制。**`tests/support/web.ts` 必须用"读写分离"的 duplex 对（`Duplex.from({readable, writable})`）或真 socket，不能用单个 `PassThrough`。**

### 对实现的影响

- hub 用 `new WebSocketServer({ noServer: true })`，在 `webServer.registerUpgrade({ path: '/marshal/uplink', handler })` 里调 `handleUpgrade`；不要自建 `http.Server`、不要 `new WebSocketServer({ port })`。
- 未命中路由时 DSH 会 `socket.destroy()`（`<dsh-checkout>/packages/host/webserver/src/index.ts:603-606`），所以 `/marshal/uplink` 必须是精确路径，`/marshal` 的普通 HTTP 路由不会截走升级请求。

## 接缝 2：`sessionController.follow()` 在无 Remote 请求上下文时是否可用

### 结论：OK

### 证据

1. **`follow` 是纯委托，实现体不碰调用身份。** `<dsh-checkout>/packages/api/session-controller/src/index.ts:607-609`：

   ```ts
   @Remote({ mode: 'stream' })
   follow(request: SessionFollowRequest, signal: AbortSignal): AsyncIterable<SessionFollowFrame> {
     return this.webController.follow(request, signal)
   }
   ```

2. **真正实现只用 `ctx` 做生命周期与监听注册。** `<dsh-checkout>/packages/api/session-controller/src/web/controller.ts:32-79`：`ListenerBuffer`、`EventListener`、`historyController.usingObservation`、`resolveHistoryRequest` / `validateObservationAddress`，全部与请求身份无关。

3. **`grep` 证据。** 在实现目录里搜身份访问，零命中：

   ```
   $ grep -rn "invocation\|principalOf\|remoteAccess" \
       packages/api/session-controller/src/web/*.ts \
       packages/api/session-controller/src/history/*.ts
   （无输出，exit 1）
   ```

   整个 `index.ts` 里三处身份读取都与 `follow` 无关：`principalOf` 只在 `prompt`（`:481`），`remoteAccess.allows` 只在 `list`/`search`（`:281`、`:295`）和 `control`（`:633`、`:638`）。

4. **`@Remote` 只是标记，不改写方法。** 装饰器仅写入 marker，供 typert 生成器静态分析（`<dsh-checkout>/packages/typert/protocol/src/index.ts:282-317`）；没有任何运行时包装要求"必须在 Remote 调用中"。

5. **即使有人读 `ctx.invocation` 也不会抛。** 第一个 Remote 服务构造时会在 `ctx.root` 注册 accessor，让 `ctx.invocation` 在 Remote 调用外读作 `undefined`（`<dsh-checkout>/packages/typert/protocol/src/index.ts:266-275`），而不是 reflect 的 "cannot get property" 错误。

6. **DSH 自己的测试就在进程内直接 `follow`。** `<dsh-checkout>/packages/api/session-controller/tests/transport.host.spec.ts:94-99` 用普通 `new Context()` 组出 `WebController`，`:108`、`:143`、`:165`、`:208` 等处直接 `web.follow({ address }, signal)` 并消费快照/事件帧，全程没有 gateway 或 Peer。

### 注意事项（不改变 OK 结论，但影响 Task 9/10）

- **不做可见性过滤。** `list`/`search`/`control` 会用 `ctx.remoteAccess.allows` 裁掉他人会话，`follow` 不裁。v0 的 node 是单用户、本机可信进程，这没问题；但 hub 不能把"DSH 已鉴权"当成前提——设备与浏览器的鉴权仍按架构 §9 自己做。若将来一个 node 服务多用户，需要在适配器里补过滤。
- **`activate` 有副作用。** `request.activate === true` 会在交付 snapshot 前触发后台 `promote()`，也就是**恢复/唤起 Agent**（`web/controller.ts:62-78`，`index.ts:250-261`）。v0 的"观察"必须传 `activate: false`（省略即 false），只有用户显式"续跑/接管"才置 true，否则点开列表就会把休眠会话叫醒。
- **思考流要显式开。** `assistantStream` 省略时不会有 `{type:'assistant-stream'}` 帧（`web/controller.ts:38-40`），设计里的"思考/工具实时卡片"必须传 `assistantStream: true`。
- **请求最小形状**（`<dsh-checkout>/packages/api/session-controller/src/types.ts:487-493`）：`{ address: { kind: 'session', sessionId }, maxMessages?, turnWindow?, activate?, assistantStream? }`，除 `address` 外都可省略。

→ 架构 §7 里"退回 `events()` 500ms 轮询"的退路**不需要启用**。

## 接缝 3：`/marshal` 与 `/marshal/uplink` 是否被现有插件占用

### 结论：OK

### 证据

```
$ cd <dsh-checkout>
$ grep -rn "path: '/marshal" packages
（无输出，exit 1）

$ grep -rn "'/marshal" packages apps --include="*.ts" --include="*.tsx" --include="*.html"
（无输出，exit 1）
```

抽查现有路由注册（非测试），命名空间如下，均与 `/marshal` 不交叉：

| 路径 | 位置 |
|---|---|
| `/api`（prefix） | `<dsh-checkout>/packages/client/connection/src/index.ts:144-160`（常量见 `api-path.ts:7`） |
| `/connect`（exact） | 同上 `:161-164` |
| `/plugins`（prefix） | `<dsh-checkout>/packages/client/modules/src/index.ts:232`、`:703` |
| `/api/remote.mux`（upgrade，exact） | `<dsh-checkout>/packages/api/gateway/src/stream-protocol.ts:7`，注册于 `<dsh-checkout>/packages/api/gateway/src/index.ts:273-309` |
| `/inspector/devtools` | `<dsh-checkout>/packages/experimental/inspector/src/host/plugin.ts:17`、`:129` |
| `/desktop-smoke*`（仅 smoke 脚本） | `<dsh-checkout>/apps/desktop/scripts/smoke-runtime.ts:55` 起 |

两点补充：

- **抢占优先级对我们有利。** 匹配顺序是"exact → 最长 prefix → 唯一 fallback"（`<dsh-checkout>/packages/host/webserver/src/index.ts:650-665`）。DSH Web 壳只注册了 fallback（`<dsh-checkout>/packages/host/frontend-static/src/index.ts:152`），因此我们注册的 `/marshal` prefix 会先于 SPA fallback 命中；`/marshal/uplink` 另走升级表，与 HTTP 表互不影响。
- **撞车会大声失败。** 重复 `(kind, path)` 在注册时直接 `throw`（`register` `:445-451`、`registerUpgrade` `:460-466`），不会静默覆盖。将来 DSH 若占用了 `/marshal`，会在插件加载时立刻报 `duplicate … route`，届时按架构 §7 换前缀即可，不需要改内部路由表。

## 已读源码确认的三条事实

行号已按当前 checkout 校正；与计划中的行号差异属注释行偏移，内容一致。

### 1. `user-questions/request` 是 waterfall，返回答案即认领

- 事件声明带 `@mode waterfall`，文档原文："Return an answer to claim the request or call `next()` to delegate"，且是 agent 作用域分派：`<dsh-checkout>/packages/interaction/user-questions/src/types.ts:164-176`。
- 提问方用 `ctx.waterfall('user-questions/request', request, noAnswerer)` 派发：`<dsh-checkout>/packages/interaction/user-questions/src/index.ts:347-352`。
- `userQuestions.answer(agent, callId, batch)` 只结算 `continued` 状态：`continued()` 过滤 `question.state === 'continued'`（`:152-154`），`answer()` 找不到就 `return false`（`:170-173`）。live 提问没有通用结算入口。

→ v0 的桥接按"监听 waterfall、返回答案即认领"实现；`answer()` 只作 v1 补偿，不要用于 live 提问。

### 2. 跟随帧的三种形状

`<dsh-checkout>/packages/api/session-controller/src/types.ts`：

- `SessionFollowFrame = { type:'snapshot', … } | SessionEventEntry | { type:'assistant-stream', frame }`（`:554-565`）。
- `SessionEventEntry = { type:'event', event: SessionWireEvent }`（`:423-426`），而 `SessionWireEvent` 正是 `{ type, seq, time, data, ignorable?, sourceEventSeqs?, surfaceOp? }`（`:455-464`）。
- `SessionAssistantStreamFrame = { type:'start' } | { type:'chunk' } | { type:'end' }`（`:515-547`）；`end.outcome` 为 `committed`（带 `eventType`/`seq`）或 `abandoned`。

### 3. 流式块类型只有七种

- 权威定义：`StreamChunk` 联合恰为 `block-start | text-delta | reasoning-delta | tool-call-delta | block-end | usage | finish`（`<dsh-checkout>/packages/llm/llm/src/types.ts:496-513`）。
- `AssistantStreamAccumulator.push` 对以上七种穷举，default 走 `assertNever`（`<dsh-checkout>/packages/llm/llm/src/assistant-stream.ts:113-175`；`block-start`/`block-end`/`usage`/`finish` 在 `:168-175`）。计划引用的 `assistant-stream.ts:113` 是这段穷举的起点，联合类型本体在 `llm/src/types.ts:496`。
